状态：用户于 2026-10-18 明确授权完成整个正式矩阵及阶段 profiling，持续执行至本轮实验完成。
此前一小时运行门槛排查已结束；本轮包含测量入口校验、实际窗口读取验证、正式计时和独立 profiling。

按用户最新澄清，采用简历第一个项目中“性能对比与研究背景”的条件与指标，
作为发现瓶颈的实验标准。该标准不预设研究方案或收益；简历里的性能数值不作为测量输入。
先完成测量、定位和分析，再决定下一项研究。

## 三组对比

| 组别 | 生成方法 | Draft 读取范围 | K |
| --- | --- | --- | --- |
| 原生 AR | Target 自回归生成 | 无 Draft | 不适用 |
| 原生 DSpark Full KV | Target + DSpark Block-7 Draft | 完整历史 KV | 7 |
| DSpark Sliding Window | 相同 Target / Draft；独立副本中的最小接线修正 | Draft 最近 2176 token 的窗口配置，页对齐后逐轮审计 | 7 |

窗口组的 Target 仍读取完整上下文；缩短 Draft 读集合不等于减少全部 KV 存储。
本阶段不启用历史锚点、在线检索或其他待研究候选。

## 先检查窗口是否真的生效

实际运行库存在 `draft_window_size` 和 `SlidingWindowAdapter`，但必须确认 DSpark 的实际调用路径，
以及窗口应用后 metadata 是否被后续 builder 重建覆盖。
必须检查实际读取范围、页边界、query/bonus token 计数、绝对位置及原始写入地址。

2176 是配置窗口长度。若分页对齐使实际读取 token 数变化，逐轮记录真实值；
未经验证不能把它称为严格固定的 2176-token 读取预算。
优先核对框架已有实现的生效情况，再决定是否需要任何最小适配，并单独说明其性质。
配置入口存在或加载成功，都不算窗口读取验证通过。

## 固定实验条件

- 同一台服务器、同一可见 NPU、同一冻结软件和模型 revision；BF16，贪心生成，seed=42。
- Target 使用统一的 Model Runner 和执行模式；两种 DSpark 配置使用相同原生 eager Draft。
- 输入长度为实际编码后的 4096、16384、24576 token；1K 仅用于当前运行门槛检查。
- 实际输出固定为每请求 512 token，统一忽略 EOS。另做自然终止质量检查时单独标注。
- 先固定并发 1 完成三组、三个长度，再单独测试并发 4：共 18 个正式配置。
- 同一长度、并发的三组使用逐字节一致的请求文件。跨长度使用同类任务、相同问题和记录清楚的填充规则。
- 模型最大长度统一为 32768；显式冻结调度、chunked prefill、图捕获、KV 分配和缓存配置。
  正式任务已显式固定最大长度；旧诊断入口随输入改变上限的结果单独保存。
- 统一 `gpu_memory_utilization=0.8`，记录各方法实际 KV 分配与缓存容量，不随输入长度手工调整。
- 固定实际 `max_num_scheduled_tokens=4096`；AR 的物理输入容量为 4096，DSpark 为
  `4096 + 6 × concurrency`，满足 K=7 时框架的额外槽位要求。保存实际解析后的配置，不能只比较传参数值。
- 前缀缓存关闭；配置和 workload 冻结后，每组统一预热 10 次、测量 10 次，串行运行。

此前单输入诊断在预热 3 次后仍观察到 DSpark 开头样本的耗时下降，故本轮统一增加至 10 次。
保存全部预热和测量耗时，继续检查趋势；不事后筛掉较慢值。

并发 1 与并发 4 分开分析；如并发调整同时改变了图捕获或调度参数，必须明确记录。
跨长度的内容变化可能改变接受率，不能把所有变化都归因于 KV 读取量。
本轮 Target 均为 `FULL_DECODE_ONLY`，原生解析的捕获尺寸为：AR 并发 1 `[1]`、并发 4 `[1,2,4]`；
DSpark 并发 1 `[1,2,4,8]`、并发 4 `[1,2,4,8,16,24,32]`。
多 token 验证与 AR 的单 token 步具有不同工作量；实际 FIA 输入形状保留在 kernel CSV 中。

## 测量与正确性

每次保存请求哈希、实际输入/输出长度、完整输出 token、生成耗时、原生请求时间统计和投机计数。
同组重复先检查输出稳定性，再检查三组的 greedy 输出一致性；差异保留并定位，不静默跳过。
单一短输入一致不代表整个矩阵已经通过。
完成原生入口核验后仍出现同方法跨次差异时，保留真实比较标记、补足全部十次测量，
分别报告每请求的输出变体、AR 一致次数和同方法控制一致次数。不得重试至一致、筛选轮次或改写标记。

准备阶段发现：仅把物理容量统一为 4096 时，DSpark 的实际调度预算为 4090，导致 4K prefill 分块不同。
原生 Full KV 的采集前后输出一致，但与 AR 在第 102 个 token 起分叉；这是实际发现，不能写成一致性通过。
本轮显式校准实际预算后重测，并逐配置报告 AR 对照是否一致、公共前缀及同方法重复是否稳定。
若仍有差异，性能表保留原生观察，但不将其称为已经验证的无损加速；数值原因在缺少 logits 证据时保持假设。

报告总耗时中位数、样本波动、含 prefill 的离线输出吞吐、真实 TTFT 和请求级 TPOT。
先验证计时接口与原生生成接口的输出一致；同一图中的性能数据使用相同计时方法。
最终统一调用原生 `LLM.generate`，保留其 `FINAL_ONLY` 处理，只在请求完成时读取已有的
`RequestStateStats` 和 `FinishedRequestStats`。旧直接 engine 入口与逐 token 观察尝试单独保留。
TTFT 取原生 frontend 的 `first_token_latency`；TPOT 取 core 单调时钟的首末 token 差除以 511。
墙上时钟与单调时钟的绝对值不可混减，也不能从总吞吐倒推请求指标。

接受率使用测量区间内的 accepted / drafted token 计数。
平均接受长度按约定计算 `1 + accepted_draft_tokens / draft_steps`，注明包含 bonus token，
同时保存实际输出量和尾部截断情况；不平均日志中的滚动平均值。
记录 worker 启动后的 NPU 分配、预留与 KV 容量。动态活跃块数不可获得时保持缺失，
不把启动阶段 peak allocation 写成正式生成的峰值；缩短 Draft 读集合不等于缩减预分配 KV 容量。

## 独立 profiling：先定位，再解释

计时与 profiling 分开运行，采集实际执行 worker 的 CPU/NPU Timeline 和 kernel 明细。
每个 profiling 配置预热 3 次、运行一次未采集的原生控制，再生成 512 token，采集前 64 个 worker 迭代。
按 attention metadata 标注大块 prefill、混合路径和小 query 路径，另由原生请求统计给出语义阶段间隔。
Target 图回放的 NPU kernel 未完整关联到 CPU 作用域时，使用 graph model ID 和每回放 36 层 FIA 计数交叉归因。
独立采集条件下的输出差异如实记录，不要求它与未采集控制逐 token 一致，也不将差异标为通过。

| 环节 | 要回答的问题 |
| --- | --- |
| Prefill | 上下文增加的成本有多少发生在生成开始之前？ |
| Target 执行 | 单 token 生成和多 token verification 的单次成本、调用数如何变化？ |
| Draft Attention | 完整历史与窗口的 kernel 和读取准备成本差多少？ |
| Draft 其他计算、Markov Head | Attention 之外是否还有主要成本？ |
| 采样、metadata 和主机等待 | 是否存在显著同步、调度空隙或索引准备成本？ |
| 接受长度 | 减少读取是否改变每轮接受量，从而增加验证轮数？ |

kernel 时间与 host 作用域分别解释；有重叠时不能简单求和当作端到端耗时。
只有实际采集到的 AI Core 或带宽计数器才用于利用率结论，缺失项明确标注。

## 本阶段交付与后续确认

正式计时阶段交付三组的耗时/吞吐曲线、TTFT/TPOT 曲线、接受长度曲线和原始数据。
阶段拆分图、代表性时间线由独立 profiling 运行补充；该阶段已获用户本轮授权，计时样本不与采集样本混用。
分别计算 AR 与 DSpark、Full KV 与窗口的同条件耗时比，解释输入长度和并发变化下的收益及回退。

结论按“观察到的现象 → 阶段证据 → 候选原因 → 下一项可区分原因的实验”组织。
测量只支持现象时就保留不确定性；窗口不提速也属于有效发现。
本轮完成测试和瓶颈分析后，再决定后续历史 KV 研究，不预先指定优化收益。
